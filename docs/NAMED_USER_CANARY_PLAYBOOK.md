# Named User Canary Playbook

## Purpose and boundary

This is a controlled Preview usability study for one de-identified Quality
Case. Its purpose is to learn whether three non-specialists can complete the
Supplier Guided flow, internal review, customer review, and effectiveness
verification without Quality-system training.

It is not a Production launch, a customer acceptance claim, a certification,
or a Quality-system audit. Do not use real customer names, product drawings,
lot numbers, photos, email threads, or personal data.

Collect the participant roster through an approved internal channel, not in a
commit, issue, or observation document. Use initials or `CU-01`, `SU-01`, and
`CR-01` in the log.

| --- | --- | --- | --- |

### Access issuance procedure

1. Confirm the branch alias resolves to the Ready deployment above.
2. In Vercel, create a temporary protected-deployment share link for this
   deployment. Send it only to the named participant by the approved channel.
   Ask the participant to open it once in the browser they will use for the
   test; it must not be forwarded.
3. Coordinator creates the Case and sends Supplier/Customer invitations from
   the in-product task composer. The system sends the opaque task link by
   Preview Resend. If delivery fails, copy the generated link only into the
   approved participant channel and record `delivery_fallback`.
4. Set each external task expiry to the study end time or earlier. Revoke every
   unused task immediately after the session.
5. Never paste a task link or Vercel share link into the observation log,
   screenshots, chat, source control, or a calendar invitation.

## De-identified case card

Give only the role-relevant facts below. The scenario is deliberately
incomplete so that the Guided Investigator has a reason to ask plain-language
follow-ups.

| Field | Synthetic fact |
| --- | --- |
| Case title | `CANARY — Injection-molded housing flash affects assembly` |
| Product | `IMH-27 plastic housing` |
| Customer / requester | `Canary Customer (test)` |
| Supplier | `Canary Molding (test)` |
| Complaint | Of 1,000 shipped parts, 20 have flash at the mating edge. The flash interferes with customer assembly. |
| Discovery | Customer incoming/assembly inspection; exact shipment and batch reference are not initially known. |
| Initial containment | Supplier may state only that affected stock is being located; no verified quantity or inspection record is supplied. |
| Initial Supplier response | `员工未发现、加强培训。` |
| Deliberately missing | Mold/cavity identification, shift/date, production batch, measurement method, containment scope, inspection record, durable prevention, validation sample/criteria/result. |
| Safe evidence | A synthetic text/PDF record or a clearly watermarked test photo. It must say `CANARY TEST — NOT A PRODUCTION RECORD`. |

Facts available only when the Supplier asks a clarifying operational question:

- The operator used visual judgement only; there was no approved flash limit
  sample or measurement gauge at the trimming station.
- The final check sampled one finished carton and did not distinguish mold
  cavities. The 20 nonconforming parts were found at the customer's assembly
  point.
- A realistic corrective direction is to identify the mold condition, define a
  measurable acceptance limit, add an in-process check with recorded cavity
  traceability, and verify across several production lots. Do not volunteer
  this direction before the participant has attempted their own answer.

## Participant scripts

### Coordinator: first pass

1. Start a timer when `/cases` first loads. Without explanation, create the
   Case using the case card. Record when the first meaningful action occurs.
2. Create a Supplier task with a due date three business days ahead. Send the
   invitation to `SU-01` through the approved channel.
3. Do not explain 8D, 5 Why, PDCA, Poka-Yoke, CAPA, root cause, or what a good
   answer looks like. If asked, say only: “Please use the information that is
   available to you in the test case.”
4. After Supplier submission, review the package. Decide whether to request
   more information or prepare a Customer response. Record whether the
   coordinator can identify the recommended next action without coaching.
5. Confirm only information the coordinator understands and considers fit for
   Customer communication. Run the Customer draft; it remains a draft until
   human-confirmed text is used.

### Supplier: Guided investigation

1. Start a timer at first page paint. For the first 30 seconds, do not receive
   help. Record whether the next action is understood.
2. Answer the first prompt exactly with `员工未发现、加强培训。` where it fits
   naturally. Continue in ordinary Chinese using only the scenario facts.
3. Upload one watermarked synthetic evidence file when an evidence request is
   shown. Do not upload actual production evidence.
4. When asked about occurrence, escape, prevention, or validation, answer only
   what is known. “需要核实” is an acceptable response; do not invent a mold
   setting, sample size, result, date, or approval.
5. Complete Readiness Check and submit. The check is advisory; record any
   point where its wording is misunderstood. Do not switch to Expert Mode
   unless the participant independently chooses it; record that choice.

Expected AI safety behaviour to observe, not to teach:

- `员工未发现` must be treated as a direct observation, not a confirmed root
  cause; the next question should explore process controls and why detection
  failed.
- `加强培训` must be challenged as potentially insufficient by asking about a
  durable process, tool, standard, or error-prevention change.
- `100%检查` must not automatically be accepted as permanent prevention.
- `已验证有效` must trigger questions about method, sample/scope, acceptance
  criteria, actual results, and evidence.

### Customer: review and decision

1. Read the English Customer Review page without a briefing on internal
   workflow. Confirm that only a human-confirmed response and authorised
   evidence are visible.
2. First choose **Request Changes** and leave a field-level comment on Root
   Cause or Verification, for example: “Please explain why the existing
   inspection did not find this issue and provide validation data.”
3. After the Coordinator sends a revised snapshot, open the new Customer link
   and choose **Accept Response**. Acceptance must move the Case to Customer
   Accepted, not Closed.

### Verification and closure

1. Coordinator creates a Verification Plan containing method, owner,
   organisation, planned/due dates, sample size, scope, and measurable
   acceptance criteria. A suitable synthetic plan is: three consecutive lots,
   200 parts each, cavity traceability recorded, zero flash above the approved
   limit.
2. Supplier/Coordinator records synthetic execution and result evidence,
   submits it, and Internal reviewer approves it.
3. Confirm status becomes Verified Effective. Only an authorised internal user
   may close the Case. Then reopen it once and record the audit trail; do not
   delete historical verification data.

## Observation rules

- The observer is silent during task execution. They may answer only access,
  browser, or scenario-fact questions; record every intervention.
- Do not rephrase an AI question, explain quality terms, point out a button,
  or suggest a decision. A participant may stop at any time.
- Record behaviour, direct short quotes, timestamp, screen/stage, and outcome;
  do not record passwords, tokens, raw email addresses, customer data, or full
  free-text answers.
- A reproducible blocking access/security fault is P0. A failure that prevents
  completing a role task or invalidates the Guided learning result is P1. A
  confusing but recoverable issue is P2.
- Do not modify product UI before the first session except to fix a confirmed
  P0 access or security blocker. Record the evidence and the exact fix before
  rerunning the affected role.

## Metrics and source of truth

| Question | Primary source | Fallback / limitation |
| --- | --- | --- |
| First open to first action | Observer timestamps in the observation log | The product does not currently persist page-open telemetry for external tasks. |
| Supplier 30-second orientation | Observer outcome at 00:30 | Record `understood`, `unclear`, or `asked_for_help`. |
| Guided completion rate | On-screen answered/total plus Guided Session/Answer audit rows | Do not infer completion from a page view. |
| Return/interruption position | Observer records stage label and time; compare subsequent Answer timestamps | Browser close/reopen is not automatically classified. |
| Supplier submit attempts | Supplier Confirmation and Submission Audit | Record any UI retry separately. |
| Internal returns | Case Activity, follow-up task, and observer record | Distinguish a request for evidence from a full reinvestigation. |
| Customer Request Changes / Accept | Customer field comments and Case Activity | Customer sees only frozen, authorised content. |
| Closure | Verification Audit and Case status | Customer Accepted alone is not a closure signal. |

## Exit criteria and cleanup

The session is valid only if all three people reach their intended role action,
the Customer cannot see internal/AI/Supplier-original content, and the Case
cannot close before Internal Verification Approval.

At the end of the study:

1. Export only the redacted observation log and issue list.
2. Revoke Supplier and Customer tasks; delete synthetic evidence through the
   Case evidence controls and verify only the exact Case evidence paths are
   removed from R2.
3. Remove the Coordinator test account and all Case records, or delete the
   dedicated Neon project after preserving the redacted log. Do not delete a
   shared Preview database.
4. Remove the RC branch-specific `DATABASE_URL` and any temporary Vercel share
   links. Keep R2 Preview credentials and the RC code branch unchanged.
5. Confirm no test token, cookie, link, recipient, raw answer, or evidence file
   appears in Git, documentation, screenshots, artifacts, or logs.

## Known limitations before first session

- **Current browser-preflight hold:** `NUC-BQA-03` is P0. The Supplier UI can
  complete Guided questions but cannot upload evidence, inspect Readiness,
  confirm a Response Package, or submit it. Do not invite named users until
  the issue is fixed and the three-role browser preflight is rerun; see
  `docs/NAMED_USER_CANARY_BROWSER_QA.md`.

- The roster and participant consent are still required before invitations can
  be sent. No named person, email, task token, or account was created during
  environment preparation.
- Preview Deployment Protection requires a facilitator-issued temporary
  Vercel share link before an external task link can be opened. Participants
  do not need Vercel credentials or developer configuration.
- Guided first-open and interruption analytics are intentionally not product
  telemetry today; the observer log is the controlled measurement source.
- The default Guided Mode is the only mode in scope. The current Expert Mode
  display is not a substitute for a completed Expert-mode usability test; if
  a participant enters it and cannot continue, classify it at least P1 for
  that participant path.
- If the AI provider is unavailable, answers can still be saved, but the
  Guided AI experience is not validly tested. Record it as P1 and reschedule
  the Supplier session after Preview AI availability is restored.
