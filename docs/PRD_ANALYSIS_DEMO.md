# 8D Report Tool — PRD 专家分析报告

> 以下分析由 **编程专家 / PRD 分析师** 角色按照系统化方法论完成。
> 这份演示展示了专家如何深度分析一份 PRD，从根本需求挖掘到技术落地。

---

## 1. 产品核心理解

**一句话定位**：面向全球质量工程师的移动优先 8D 报告创建 SaaS 工具，核心价值是"现场完成报告，无需回办公室二次处理"。

**目标用户画像**：
- **主要用户**：制造业质量工程师（CQE/PQE/SQE），日常工作被 8D 报告占据大量时间
- **工作场景**：大部分时间在车间/产线/客户现场，用手机操作
- **核心痛点**：需要在现场发现问题后，拍完照回到电脑前手动填写 Excel 模板——效率极低

**核心价值主张**：
- 移动端可以直接拍照、填表、导出，一站式完成
- 标准化的 8D 流程引导，降低使用门槛
- 云端存储 + 分享链接，替代邮件来回发送

## 2. 需求深度分析

### 2.1 表面需求 → 根本需求映射

| 表面需求（PRD 写的） | 根本需求（用户真正需要的） | 分析 |
|---------------------|--------------------------|------|
| 通用 8D 模板表单 | 不想被主机厂专用模板束缚，但要满足基本的 8D 标准 | PRD 选择了正确的 MVP 策略——先通用再垂直 |
| PDF 导出 | 给客户/上级看的正式交付物，不是给自己看的草稿 | 导出格式决定了"专业感"，封面设计比内容表格更重要 |
| 附件上传（照片+文件） | 8D 报告的证据链，照片是"眼见为实"，文件是"数据支撑" | 这是该产品的核心差异化价值——手机拍照直传 |
| 分享链接 | 替代微信/WhatsApp/邮件发 PDF | 只读链接是更可控的分享方式，但用户可能更习惯直接发文件 |
| 配额机制（5 份免费） | 防止白嫖、引导付费，但不能赶走真实的个人用户 | 这个平衡点设计得很好 |

### 2.2 隐含需求清单

PRD 中没有明确写出，但落地时必须考虑的：

| # | 隐含需求 | 技术影响 | 优先级 |
|---|---------|---------|--------|
| 1 | **离线能力**：工厂车间网络往往很差 | 需要考虑 Service Worker 缓存、乐观更新、离线草稿 | P1 |
| 2 | **数据安全**：质量报告涉及客户信息、产品缺陷数据 | 需要 RLS、传输加密、附件权限控制（分享链接是否能下载附件？） | P0 |
| 3 | **多时区支持**：全球用户 | 数据库中时间戳统一 UTC，前端按用户时区显示 | P1 |
| 4 | **报告编号冲突**：多用户同时创建 | 使用 `serial` 类型的原子递增无法满足；需要用序列号服务或 UUID 前缀 | P1 |
| 5 | **富文本编辑器在移动端的体验** | TipTap 在手机上编辑体验不佳，考虑简化或分字段输入 | P2 |
| 6 | **附件存储成本**：R2 有免费额度但超出后按量付费 | 需要定期清理未完成报告的"孤儿附件" | P2 |
| 7 | **Webhook 安全**：Creem webhook 签名验证 | 必须在服务端验证签名，防止伪造支付回调 | P0 |

### 2.3 功能优先级矩阵

| 优先级 | 功能 | 理由 |
|-------|------|------|
| **P0** (必须有) | 认证系统、D0-D8 表单、附件上传、PDF 导出 | MVP 核心闭环 |
| **P0** | 数据库 RLS、支付 webhook 验证、邮箱验证 | 安全合规，不可妥协 |
| **P1** (应该有) | 分享链接、Word 导出、i18n（中/英）、Zip 打包 | 显著提升产品价值 |
| **P1** | 报告列表/仪表盘、配额系统、注册限流 | 运营必需 |
| **P2** (锦上添花) | Logo 上传、5-Why 表格 | 专业感加分 |
| **P3** (后续) | SCAR、看板、甘特图、主机厂模板 | Phase 2 内容 |

## 3. 技术关键问题

### 问题 1：移动端拍照上传的完整流程设计

**背景**：这是产品的核心差异化功能。用户在现场用手机拍照 → 照片直接关联到 8D 报告某一步骤。

**关键设计决策**：
- **拍照 vs 相册**：`<input capture="environment">` 直接调起相机，但图片可能很大（现代手机 5-10MB/张）。必须在客户端做压缩。
- **上传策略**：使用预签名 URL 直传 R2，不经过服务器中转。这是正确的设计——避免了 Vercel Serverless Function 的 body 大小限制（4.5MB）。
- **隐患**：如果预签名 URL 过期（5 分钟），或用户在上传过程中切到后台（手机端常见），需要重试机制。
- **推荐**：上传前先压缩图片到 1920px 宽（前端 Canvas API），再上传。这对于文档类照片足够了。

### 问题 2：Next.js 14 App Router 的路由设计约束

**背景**：PRD 选择 Next.js 14 App Router + RSC（React Server Components）。

**关键考量**：
- **Cookie-based i18n（next-intl）**：不修改 URL 是好的（保持 URL 干净），但意味着所有页面不能被 CDN 按语言缓存。对于营销落地页（`/`、`/pricing`），建议单独处理——用 `[locale]` 前缀路由，这样才能被 CDN 缓存。
- **Server Components 边界**：D0-D8 表单是高度交互的，大部分应该是 Client Component。数据获取（报告内容）可以通过 Server Component 的 `async` 函数完成，然后通过 props 传给 Client Component。
- **Better Auth + RLS**：Better Auth 使用 JWT，数据库层面通过 `set_config('app.current_user_id', ...)` 设置当前用户——这在 Server Component 和 API Route 中工作良好，但在 Client Component 的直接数据库查询中不适用。当前设计（通过 API Route 隔离）是正确的。

### 问题 3：配额消耗的"完整使用"检测

**背景**：免费用户 5 份配额，需要满足 5 个条件才算消耗 1 份配额（完成 8 步骤 + 50% 字段 + 1 附件 + 导出 PDF + 保存 3 次）。

**技术挑战**：
- 这些条件需要在多个用户操作中累计检测（保存触发、导出触发、上传附件触发）
- 使用 `report_edit_history` 表跟踪是好的设计
- **隐患**：条件 4"导出 PDF"——如果用户导出多次 PDF，只在第一次消耗配额？每次导出都扣？PRD 没说明白。
- **推荐**：配额消耗应是一次性的（首次满足所有条件时），之后该报告的所有导出都不再消耗。在 `reports` 表的 `has_consumed_quota` 字段标记。

### 问题 4：Drizzle ORM 的迁移策略

**背景**：PRD 使用 `drizzle-kit push` 进行数据库变更。这适合早期开发，但进入生产后需要更稳妥的迁移策略。

**推荐**：
- MVP 阶段：`drizzle-kit push` 没问题
- 生产上线后：切换到 `drizzle-kit generate` + `drizzle-kit migrate`，生成 SQL 迁移文件，纳入版本管理
- 特别是涉及 `alter table` 添加 `logo_url` 字段这类变更，必须用迁移文件确保可回滚

## 4. 技术方案评估

### 4.1 技术栈评审

| 组件 | PRD 选择 | 评价 | 替代方案 |
|------|---------|------|---------|
| 前端框架 | Next.js 14 App Router | ✅ 正确选择。SSR/SSG/ISR 对营销页 SEO 友好 | - |
| 样式 | Tailwind CSS + shadcn/ui | ✅ 开发效率高，移动端响应式友好 | - |
| 数据库 | Neon (Serverless PG) | ✅ 与 Vercel 边缘函数天然适配 | PlanetScale（也是 serverless，但 MySQL） |
| ORM | Drizzle ORM | ✅ 类型安全、轻量、SQL-like API | Prisma（更重但生态更成熟） |
| 认证 | Better Auth | ⚠️ 相对较新的库，文档和社区较小 | Auth.js (NextAuth) 或 Clerk |
| 存储 | Cloudflare R2 | ✅ 无出口流量费，S3 兼容 | Uploadthing（更简单但更贵） |
| 支付 | Creem | ⚠️ 对国内团队，可能需要支付宝/微信支付 | Stripe（生态第一，但门槛高） |
| PDF 导出 | jsPDF（客户端） | ⚠️ 客户端生成，复杂排版能力有限 | Puppeteer（服务端，但 serverless 不友好） |
| Word 导出 | docx (npm) | ✅ 服务端生成，排版能力强 | - |
| ZIP 打包 | jszip（客户端） | ✅ 轻量，不需要服务端处理大文件 | - |
| i18n | next-intl v4 | ✅ 原生支持 RSC，类型安全 | - |

### 4.2 Better Auth 风险评估（重点）

Better Auth 是一个相对较新的认证库。它的优势是轻量、类型安全、支持多种认证策略。但作为 MVP 的核心基础设施，认证出问题影响面最大。

**需要注意的点**：
1. JWT token 刷新机制是否可靠？（长期在线用户 session 过期体验）
2. OAuth 回调在 Vercel 边缘环境是否稳定？
3. 与 Neon PostgreSQL 的连接池是否兼容？（Neon 有连接数限制）

**缓解方案**：如果 Better Auth 在生产中出现问题，迁移到 Clerk 或 Supabase Auth 作为备选。认证逻辑应该通过抽象层隔离（当前 `/api/auth/[...all]/route.ts` 已经做得很好）。

### 4.4 数据模型核心设计要点

当前 PRD 的 ER 图设计得相当完整。几个值得注意的点：

1. **`reports.data` JSONB 字段**：存储 D0-D8 所有表单数据是务实的做法（8D 步骤的字段结构因模板而异，JSONB 比严格的关联表更灵活）。但需要注意 JSONB 查询效率——如果需要"搜索所有报告中提到某个零件号"，JSONB 查询会比较慢。Phase 2 可以加 GIN 索引。

2. **`attachments.step_id`**：关联到具体步骤的设计是正确的（D2 的照片和 D6 的照片需要区分）。

3. **`report_shares.access_token`**：用于公开分享链接。建议加上 `expires_at`（PRD 已有），以及可选的访问密码（Phase 2 功能）。

### 5.1 技术风险

| 风险 | 严重程度 | 概率 | 缓解措施 |
|------|:---:|:---:|---------|
| Better Auth 生产问题 | 🔴 高 | 中 | 抽象认证层，预留 Clerk/Auth.js 迁移方案 |
| R2 预签名 URL 在移动端上传失败 | 🟡 中 | 中 | 客户端重试机制（3 次），失败后回退到服务端中转 |
| Vercel Serverless 函数冷启动慢 | 🟡 中 | 低 | 营销页面用 ISR，API 用 Edge Runtime（如有） |
| Neon 连接数耗尽 | 🟡 中 | 低 | 使用连接池（Neon 自带 PgBouncer），Drizzle 配置 pool |
| `docx` 库中文排版异常 | 🟢 低 | 中 | 充分测试中文 Word 导出，备选用 Puppeteer 生成 PDF 转 Word |

| 风险 | 缓解 |

| 用户习惯免费的 Excel 模板，不愿意付费 | 免费版 5 份是合理的体验门槛，让用户先建立使用习惯 |

| 风险 | 缓解 |

| 支付集成（Creem）可能遇到文档/API 问题 | 提前做 Creem sandbox 测试，确保 webhook 流程完整 |

## 6. 基于专业经验的优化建议

### 6.1 PRD 可以改进的地方

1. **缺少移动端的具体交互设计**：PRD 提到"移动端优先"但只给了桌面端界面规范。建议补充：
   - 移动端 D0-D8 步骤的底部导航栏设计（如何在不占用太多屏幕空间的情况下显示 9 个步骤？可以用横向滚动的步骤条 + 当前步骤高亮）
   - 拍照上传的完整交互（拍完照后是否立即显示预览？是否支持多张连拍？）

2. **PDF 导出排版需要更详细的规格**：
   - 8D 报告封面应该长什么样？（PRD 只在 v1.1.0 Spec 中提到了封面元素）
   - 照片在 PDF 中的排版方式（单列？网格？是否加边框？）
   - 5-Why 表格在 PDF 中的样式

3. **分享链接的安全模型不够清晰**：
   - 分享出去的链接，接收者能否看到附件？能否下载附件？
   - 应该可以——v1.1.0 Spec 的 ZIP 导出包含附件，暗示附件是可访问的
   - 建议：分享页面可以查看附件缩略图但不可下载（除非报告所有者在分享设置中开启了"允许下载附件"）

4. **定价策略可以考虑中国市场的差异**：
   - $9.99/月在欧美是合理价格，但在中国市场可能需要调整
   - 建议 PRD 中预留中国区定价策略（人民币定价，微信支付/支付宝集成）

### 6.2 用户体验提升建议

1. **新用户引导**：D0-D8 对于不熟悉 8D 的新手来说有学习曲线。建议在首次使用时提供简短的 onboarding（3 步介绍），每个步骤里放一个示例/占位符文本提示怎么填。

2. **自动保存提示**：PRD 提到了自动保存，但用户需要明确的反馈（"已自动保存 2 秒前"）来建立信任。

3. **报告模板选择**：MVP 只有 1 个通用模板，D0 步骤的"报告类型"选择（客户 8D vs 内部 8D）实际上可以决定表单的某些字段是否必填。这在 PRD 的"字段必填性策略"一节有提到，但可以设计得更智能——比如"客户 8D"需要填客户名称，"内部 8D"则不需要。

4. **进度可视化**：仪表盘不止是报告列表。建议每个报告卡片上显示进度条（D0-D8 完成度），让用户一眼看到哪些报告还需要继续填写。

### 6.3 架构演化建议（Phase 2 展望）

PRD 的 Phase 2 规划了很多功能。从技术角度看，有几个关键的基础设施需求应该尽早规划：

1. **文件处理 Pipeline**：当前附件上传是简单的存储。Phase 2 可能需要：图片 OCR（从照片中提取零件号）、PDF 预览缩略图生成、大文件分片上传。

2. **搜索与全文检索**：当报告数量增长后，用户需要搜索历史报告。考虑集成 PostgreSQL 的全文搜索（`tsvector`）或引入 Meilisearch/Typesense。

3. **通知系统**：当报告被分享、评论、审批时需要通知。建议尽早设计通知表结构，即使 Phase 1 不实现。
